### FIX-003: Falscher OAuth-Discovery-Pfad im `WWW-Authenticate` Header
**Status:** erledigt

**Datei:** `app/utils/auth_middleware.py`

**Beleg:**
```python
"""Return 401 with proper WWW-Authenticate header."""
base_url = str(request.base_url).rstrip("/")
auth_server = f"{base_url}/.well-known/oauth-authorization-server"
return JSONResponse(
    status_code=401,
    content={"detail": detail},
    headers={
        "WWW-Authenticate": f'Bearer realm="mcp", authorization_server="{auth_server}"'
    },
```

**Alter Zustand:**
`/v1/.well-known/oauth-authorization-server`

**Neuer Zustand:**
`/.well-known/oauth-authorization-server`

**Auswirkung des Bugs:**
OAuth-fähige MCP-Clients konnten den falschen `authorization_server` aus dem Header ziehen und dadurch fehlschlagen oder gegen den falschen Alias verhandeln.

**Validierung:**
- `py_compile` erfolgreich
- Health grün
- Backend danach lauffähig

### BUG-005: Reaktiver Fallback ist belegt, aber stündlicher spezifischer Gemini-Limit-Check ist nicht belegt
**Schweregrad:** mittel

**Bestätigt:**
Es gibt klare Fallback-/Rate-Limit-Logik in:
- `app/services/tristar/settings_controller.py`
- `app/services/agent_bootstrap.py`
- `app/services/triforce/llm_mesh.py`

**Beleg – FallbackConfig:**
```python
fallback_order: str = "gemini,groq,cerebras,ollama,mistral,cohere,openrouter,anthropic,together,fireworks,huggingface"
auto_fallback_enabled: bool = True
max_retries_before_fallback: int = 2
fallback_timeout: float = 30.0
gemini_fallback_model: str = "ollama/qwen3:30b-cloud"
```

**Beleg – Agent Rate Limiter:**
```python
if bucket["hour_count"] >= self._config["per_hour"]:
    bucket["violations"] += 1
    return False, f"Rate limit exceeded: {self._config['per_hour']}/hour"
```

**Zusätzlicher Befund – Scheduler vorhanden:**
In `app/main.py` wird der Scheduler gestartet:
```python
_scheduler.start()
_spawner.start()
logger.info("Task Scheduler + Agent Spawner gestartet")
```

In `app/services/task_scheduler.py` existieren periodische Tasks, z. B.:
- WordPress Content Engine: alle 3600 Sekunden, Agent `gemini-mcp`
- Flarum Content Engine: alle 7200 Sekunden, Agent `gemini-mcp`
- Production Health Monitor: alle 1800 Sekunden

**Wichtig:**
Damit ist **allgemeines stündliches Scheduling belegt**, aber **kein expliziter stündlicher Task nur zur Prüfung des Gemini-API-Limits**.

**Bewertung:**
- Reaktiver Fallback: ja, belegt
- allgemeiner Scheduler: ja, belegt
- expliziter stündlicher Gemini-Limit-Check: derzeit nicht eindeutig belegt

**Empfohlene Maßnahme:**
Eigenen Watchdog einführen, z. B.:
- alle 60 Minuten: `gemini-mcp` probe / health / remaining budget check
- bei Limit-Sättigung: Notification + kontrollierter Fallback-State
- optional: auto-recover nach Cooldown
